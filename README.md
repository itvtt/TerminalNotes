# Terminal Notes

상단에서 **일반 / 고급** 모드를 선택합니다. **일반 모드**는 태스크 목록 없이 터미널 하나만 조작하는 화면입니다. **▶ 실행 아이콘**을 누르면 처음 설정한 작업 폴더에서 터미널이 시작되고, 원하는 작업을 직접 입력하면 됩니다. **× 닫기 아이콘**으로 터미널을 닫습니다. 작업 폴더는 설정에서 변경할 수 있으며 실행 버튼만으로 플랜을 생성하거나 전송하지 않습니다. **고급 모드**에서 태스크 관리·플랜·플랜메이커·여러 터미널·분할 기능을 사용할 수 있습니다. 설치 확인 뒤 최초 설정에서 설명을 보고 일반·고급 모드를 선택하며 이후 선택을 기억합니다. 설정을 마친 기존 사용자는 다시 선택하지 않습니다. 여러 터미널이 열린 상태에서 일반 모드로 전환하면 닫을 터미널을 정리하도록 안내하고 기존 작업을 유지합니다. 모드 전환 시 실행 중인 세션과 미저장 초안을 보존합니다.

일반 모드의 작업 공간에는 전체 폴더 경로가 표시되며 옆의 폴더 아이콘을 누르면 해당 위치를 탐색기에서 엽니다. 긴 경로는 마우스를 올려 전체 내용을 확인할 수 있습니다. 작업 폴더 변경 아이콘은 숨기며, 설정에서 폴더를 변경하면 실행 중인 터미널은 유지하고 변경된 경로를 다음 실행부터 사용합니다. 고급 모드에서 이미 열어 둔 터미널 하나는 일반 모드에서도 그대로 이어집니다. 새 터미널을 시작할 때는 설정된 작업 폴더를 사용합니다. 과거 태스크 선택 정보와 프로젝트 폴더·파일·플랜·기록은 보존합니다.

일반 모드에서 터미널 화면 연결이 끊어지면 작업 공간의 실행·닫기 아이콘 옆에 **재연결 아이콘**이 나타납니다. 현재 터미널의 기존 대화에 다시 연결하며 새 작업 터미널이나 대화를 만들지 않습니다. 재연결 중이거나 입력·종료 정리 등으로 연결할 수 없을 때는 중복 실행을 막고 상태를 표시합니다.

플랜메이커 왼쪽의 **플랜 정리**를 누르면 확인 후 불필요한 단어·반복 표현과 불필요하거나 불분명한 항목(중복, 뜻 없는 문자열, 앞뒤가 끊긴 조각, 대상 없는 막연한 말)을 지우고, 남은 항목을 목표·기능 요구사항·화면·디자인·기술·구성·검증·완료 기준 같은 유형별 제목으로 다시 묶습니다. 정리는 별도의 **플랜 정리 창**에서 진행하며(메인 화면을 막지 않아 여러 태스크의 정리를 동시에 돌릴 수 있고, 정리 중인 태스크에서 **플랜 정리**를 다시 누르면 그 창을 앞으로 가져옵니다), 진행률(%)과 막대, 지금 단계, 경과 시간, 지나온 단계와 시각을 보여 주고 **정리 중단**으로 멈출 수 있습니다(모델이 답을 끝날 때 한꺼번에 주므로 진행률은 경과 시간과 분량으로 추정하며 되돌아가지 않고, 결과를 반영할 때 100%가 됩니다). 끝나면 같은 창에 결과와 지운 항목 전부(이유), 저장 여부가 나옵니다. 남기는 요구사항·수치·예외·경로·코드 블록은 그대로 두고, 수치·경로가 든 항목을 지울 때는 모델이 원문 줄과 이유를 제거 목록에 적어야만 받아들이며 지운 항목은 완료 알림에 이유와 함께 보여 줍니다. 긴 플랜은 부분별로 정리한 뒤 전체를 한 번 더 유형별로 묶습니다. 날짜·"(… 추가)" 같은 기록 표시, 질문 번호, 완료 표시, 진행 기록은 지우고 `Loop 모드` 구역은 그대로 둡니다. 정리 결과는 미저장 초안이며 **저장** 또는 **실행**으로 확정합니다. 정리는 OpenCode로 요청합니다(모델도 플랜메이커와 같은 것). 버튼으로 하면 정리 전용 OpenCode 터미널을 화면 밖에 열었다가 닫고, 프로젝트 터미널은 건드리지 않습니다. 플랜메이커는 확인된 내용을 받을 때마다 plan.md에 바로 저장해 중간에 끊겨도 남고, **플랜으로 돌아가기**를 누르면 플랜메이커가 바로 닫히면서 그 플랜메이커의 OpenCode로 같은 정리를 이어서 한 뒤 결과도 plan.md에 저장합니다(정리 전 플랜은 `terminal-notes\plan.before-cleanup.md`). 버튼으로 한 정리 결과는 미저장 초안입니다. 정리하는 동안에는 그 프로젝트의 플랜메이커를 시작할 수 없습니다.

요청과 기존 플랜이 길면 플랜메이커가 **기존 플랜을 정리할까요?** 확인창을 표시합니다. **정리 후 계속**을 누르면 같은 카테고리와 중복 항목을 묶고, 서로 다른 요구사항·코드·경로를 유지한 채 이어서 진행합니다. 정리 결과는 미저장 초안이며 **저장** 또는 **실행**으로 파일에 확정합니다. 조치가 필요한 경고와 오류는 상단 상태 문구뿐 아니라 자체 팝업으로 표시합니다.

모드별 사용법은 [실제 화면으로 보는 애니메이션 가이드 (HTML)](docs/TerminalNotes-실습가이드.html)를 참고하세요. 위의 탭에서 **일반**(초심자 · 터미널 하나에 말하듯 입력), **플랜**(에이전트가 방향을 잃지 않게 plan.md의 목표·순서·완료 기준대로 진행), **고급**(여러 터미널 칸에서 동시에 실행하고 Loop로 개선을 이어 가기)을 골라 볼 수 있으며, `#plan-9`처럼 주소 끝에 모드와 단계를 붙이면 그 단계부터 열립니다. 예제는 엑셀 파일의 상품별 매출을 SUMIF로 정리하는 작업입니다. **저장**은 저장만, **실행**은 저장 후 시작, **전송**은 플랜에 넣지 않고 터미널로만 보냅니다. 플랜 모드에서는 Loop를 쓰지 않습니다. [단계별 그림 가이드](docs/TerminalNotes-사용가이드.html), [그림 모음](docs/TerminalNotes-단계별-그림.zip), [한 장 PDF](docs/TerminalNotes-사용가이드.pdf)도 함께 제공합니다.

OpenCode와 일반 셸을 공통 ANSI/VT 엔진과 WebView 없는 네이티브 터미널 화면으로 표시합니다. 독립 실행형 터미널은 `Start-Standalone-Terminal.cmd`로 열 수 있습니다. 플랫폼별 지원 범위·빌드·실행 방법은 [TERMINAL-ENGINE.md](TERMINAL-ENGINE.md)를 참고하세요.

메인·설정·플랜메이커·알림창은 검정 계열 배경, 샴페인 골드 강조, 아이보리 글자로 통일합니다. 영역은 검정의 밝기 차이와 금색 테두리로 구분하며 알림창은 메시지와 닫기 버튼 중심으로 간결하게 표시합니다. 실행·입력 대기·완료 상태색과 터미널 색상은 유지합니다. 유광 표현은 정적인 그라데이션으로 만들며 장식용 상시 애니메이션이나 블러·그림자 효과를 추가하지 않습니다.

앱·제목 표시줄·트레이 아이콘도 검정 바탕에 샴페인 골드 터미널 기호로 통일합니다. SVG와 같은 도안의 PNG·여러 크기의 ICO를 제공하며, `tools/Generate-Icon.ps1`로 PNG와 ICO를 다시 생성할 수 있습니다.

OpenCode용 Windows 작업 공간입니다. OpenCode 작업 서버에 OpenCode 자체 터미널 화면을 연결합니다. 대화·도구 출력·승인·질문은 OpenCode 화면에서 처리하며, TerminalNotes가 별도의 대화 이름이나 말풍선을 덧붙이지 않습니다. 일반 모드는 작업 폴더 경로와 실행·닫기 아이콘, 터미널 하나로 구성됩니다. 고급 모드에서는 왼쪽에 태스크 목록, 항상 표시하는 플랜 문서, **플랜에 추가** 입력창·플랜메이커를 위에서 아래 순서로 배치하고, 오른쪽에 터미널을 표시합니다. 일반 셸 터미널도 계속 사용할 수 있습니다.

OpenCode 화면의 입력과 세션 메뉴는 OpenCode 자체 기능을 사용합니다. 마우스를 사용하는 화면에서는 Shift를 누른 채 드래그하여 텍스트를 선택합니다. 플랜 전송과 상태 확인은 같은 OpenCode 서버의 API로 연결하며, 전송 확인을 위해 같은 요청을 중복 제출하지 않습니다. 미전송 입력은 앱이 열려 있는 동안 유지됩니다. 한글은 조합 중인 음절을 커서 위치에 미리 보여 주고 확정된 음절만 보냅니다. 입력기가 확정 알림을 보내지 않는 환경에서도 입력란에 확정된 글자를 기준으로 순서대로 한 번씩 보냅니다.

OpenCode 터미널 본문 전체의 배경은 실제 상태에 따라 진행 중에는 녹색, 승인·질문·선택 대기에는 주황색, 그 외에는 회색으로 바뀝니다. 실제 진행 상태가 유지되면 잠시 출력이 없어도 녹색을 유지하고, 출력 애니메이션만 최근 활동 여부에 따라 멈춥니다. OpenCode가 출력한 배경색에도 상태색을 적용하며, 글자와 선택 영역은 읽을 수 있는 대비를 유지합니다.

여러 프로젝트의 새 OpenCode 터미널은 순서대로 시작합니다. 시스템 메모리나 CPU 사용량이 높으면 터미널 본문 전체에 **실행 대기 중**과 현재 대기 이유를 표시하고, 자원이 안정되면 자동으로 시작합니다. 다른 터미널의 시작을 기다리는 경우도 이유를 표시합니다. 자원 대기 시간은 터미널의 시작 제한 시간에 포함하지 않으며, 대기 중에도 다른 프로젝트의 선택·저장과 해당 작업의 중단·터미널 닫기를 사용할 수 있습니다. Loop의 다음 요청과 자동 오류 복구 요청도 같은 대기열에서 자원을 확인하며, 대기 이유를 상태에 표시하고 여유가 생기면 자동으로 이어갑니다. 기다리는 동안 중단·새 입력·종료 예약을 다시 확인하고, 전송 직전에도 현재 세션과 작업을 검증합니다. 이 조절은 새 프로세스와 후속 모델 요청의 시작을 늦추며, 이미 실행 중인 요청을 중단하거나 프로세스의 CPU·메모리를 강제로 제한하지는 않습니다.

기본 보류 기준은 메모리 사용률 85% 이상, 여유 메모리 1 GiB 미만, CPU 사용률 90% 이상입니다. 시스템 전체 커밋(Windows가 보장한 메모리)의 사용률이 90% 이상이거나 커밋 여유가 1 GiB 미만인 경우도 기다립니다. 작은 메모리 환경에서는 RAM 여유 기준을 전체 RAM의 10%, 커밋 여유 기준을 커밋 한도의 5%로 낮춥니다. 과부하 이후에는 2초 간격으로 측정하여 메모리·CPU·커밋 사용률이 모두 80% 이하이고 RAM·커밋 여유도 회복된 상태가 10초 이상 유지되면 자동으로 이어갑니다. 회복에 필요한 여유는 RAM 1.5 GiB 또는 전체 RAM의 15% 중 작은 값, 커밋 2 GiB 또는 커밋 한도의 10% 중 작은 값입니다. 기존의 최소 2초 시작 간격은 유지하며, 자원 측정에 실패하면 그 이유를 표시하고 다시 측정합니다. 정상 상태에서는 이 회복 대기를 추가하지 않습니다.

Loop 또는 자동 오류 복구가 CPU·메모리 과부하로 대기하면 프로젝트명과 대기 이유, 자원이 안정되면 자동으로 재개한다는 안내를 자체 팝업으로 표시합니다. 실행 중에도 기존 5초 자원 진단 주기로 심각한 RAM·커밋 부족을 확인해 자체 팝업으로 알립니다. 알림을 닫거나 확인할 때까지 자동 재개를 막지 않으며, 한 번의 부족 상태에서 같은 알림을 반복하지 않습니다. 터미널의 대기 상태 표시는 계속 유지하며, 일반적인 실행 순서·시작 간격 대기에는 이 알림을 표시하지 않습니다. 기존 알림 끄기와 알림 미루기 설정을 따릅니다.

장시간 Loop에서 교체·종료된 터미널의 이벤트와 참조를 해제합니다. 출력 대기열에는 상한을 두고 꽉 찼을 때만 읽기를 기다려 메모리가 계속 늘어나는 것을 막습니다. 출력 내용은 버리지 않으며, 정상 상태에 추가 지연을 주지 않습니다. 이 보호는 실행 중인 외부 프로그램을 강제로 종료하거나 Windows 재부팅을 방지한다고 보장하는 기능은 아닙니다.

작업창 안에서 Ctrl+Shift+T를 누르거나 터미널 영역의 **+ 터미널** 버튼을 누르면 현재 작업 폴더에서 독립 OpenCode 터미널 하나를 기존 화면 옆에 추가합니다. 태스크나 플랜이 없어도 바로 열리며, 태스크 등록·플랜 연결·자동 요청 전송·자동 진행을 하지 않습니다. 기존 터미널과 태스크 선택·플랜 초안·배치는 유지됩니다. 독립 터미널의 이름 변경과 중단·시작은 해당 터미널에만 적용되며, 추가한 터미널을 모두 닫으면 원래 태스크 배치로 돌아갑니다. 플랜메이커 보기에서 **+ 터미널**을 누르면 터미널 보기로 바꿔서 엽니다.

터미널 영역 상단의 버튼 하나가 실행 중에는 **■ 중단**, 종료된 상태에서는 **▶ 시작**으로 바뀝니다. 중단해도 탭과 작성 중인 플랜·입력은 남으며, 시작하면 같은 프로젝트와 위치에서 터미널을 다시 엽니다. 터미널 시작만으로 플랜을 자동 전송하지 않습니다.

상단 메뉴는 오른쪽에 정렬하며 상태 모니터 버튼은 표시하지 않습니다. 분할뷰 버튼은 제목 표시줄의 설정·창 제어 버튼 왼쪽에 작은 간격을 두고 배치합니다. 분할된 터미널은 얇은 테두리로 구분합니다. 태스크 터미널 상단에는 태스크명을, 독립 터미널에는 해당 터미널 이름을 한 줄로 표시하며, 이름을 더블클릭하거나 이름 영역에서 F2를 누르면 그 자리에서 수정할 수 있습니다. Enter 또는 다른 곳 클릭으로 저장하고 Esc로 취소합니다. 태스크명을 변경하면 태스크 목록과 함께 갱신되며 프로젝트 폴더·플랜·실행 중인 세션은 유지됩니다. 터미널 선택은 터미널 영역 상단 왼쪽, 새 터미널은 오른쪽에 배치합니다. 세로 경계의 화살표는 왼쪽 패널 전체를 접고 펼칩니다. 펼친 태스크 화면의 플랜 문서는 목록 아래, **플랜에 추가** 입력창 바로 위에 항상 표시합니다. 태스크·아카이브는 둥근 배경 안에 나란히 배치하며, 선택한 탭은 검정 배경의 명암과 샴페인 골드 테두리·글자로 구분합니다. 탭에 마우스를 올리면 배경이 반응하고 키보드 포커스는 별도 테두리로 표시합니다. 탭 아래에는 카테고리 구분 없이 모든 태스크를 한 목록으로 표시합니다.

태스크는 폴더·제목·시작/중단·Loop 버튼을 한 줄로 표시합니다. 현재 상태는 시작·중단 버튼의 아이콘과 툴팁으로 확인합니다. 태스크·아카이브 탭 오른쪽의 `new` 버튼은 새 프로젝트를 바로 만듭니다. 바로 왼쪽의 **새로고침 아이콘**은 작업 폴더를 다시 읽어 추가되거나 삭제된 폴더를 목록에 반영하고, 앱이 연 각 태스크의 plan.md도 디스크에서 다시 읽어 터미널 등 앱 밖에서 바뀐 플랜을 보여 줍니다. 미저장 초안이 있거나 플랜메이커·플랜 정리·저장이 진행 중인 플랜은 그대로 두고 그 수를 알립니다. 새로고침으로 실행 중인 터미널이나 플랜 초안을 종료·삭제하지 않습니다. 왼쪽 목록 아래의 플랜 문서 우상단에서 **플랜메이커**를 열고, 그 아래 **플랜에 추가** 입력창 하단의 저장·실행 버튼을 사용합니다.

태스크는 이름순으로 정렬하며 카테고리 생성·지정·관리 메뉴는 표시하지 않습니다. 기존 분류 데이터와 프로젝트 폴더·파일은 보존됩니다.

터미널 선택 목록은 아직 터미널을 열지 않은 프로젝트도 이름순으로 표시합니다. 처음 실행해도 작업 폴더의 일반 태스크 목록을 실행 기록보다 먼저 표시하며, 아카이브 프로젝트와 태스크들을 담는 기본 작업 폴더 자체는 터미널 선택 목록에서 제외합니다. 폴더 목록을 읽는 도중 클릭하면 로딩 안내 뒤 같은 메뉴에 전체 목록이 채워집니다. 저장된 프로젝트도 함께 포함하며, 상단에서 전체 프로젝트 수와 열린 터미널 수를 따로 확인할 수 있습니다. 열려 있는 프로젝트는 기존 세션으로 이동하며, 미실행 프로젝트를 선택하면 빈 칸에 터미널을 엽니다. 작은 분할에서는 OpenCode 화면 전체가 들어오도록 표시 배율을 자동으로 줄이며, 칸을 넓히면 원래 배율로 돌아옵니다. 빈 터미널 칸의 선택 목록도 태스크·아카이브 탭에 관계없이 일반 태스크만 표시합니다. 메뉴는 터미널 영역 안에서 열리며, 프로젝트가 많으면 스크롤하여 마지막 항목까지 선택할 수 있습니다.

태스크와 터미널에는 별도의 재실행 버튼을 표시하지 않습니다. 다시 시작하려면 **중단**한 뒤 같은 버튼의 **시작**을 누릅니다.

저장 완료·새로고침·변경 없음·정상 진행 같은 일반 안내는 창 제목 아래의 상단 상태 영역에 표시하며 팝업을 띄우지 않습니다. 오류·조치가 필요한 경고·과부하 경고는 별도의 **알림** 창으로 표시합니다. 알림 창은 최근 경고 기록을 표시하며 같은 경고가 연속되면 하나로 모읍니다. 터미널의 입력 포커스를 가져오지 않으며, 사용자가 같은 작업을 다시 시도해 실패한 경우에는 경고를 다시 보여 줍니다.

## 실행

`Start-TerminalNotes.cmd`를 실행합니다. 실행기는 먼저 x64 .NET SDK와 .NET 10 Desktop Runtime을 확인합니다. 필요한 구성 요소가 없으면 **.NET 10 SDK를 자동 설치**한 뒤 계속 진행합니다. 실행 파일이나 필수 DLL이 없으면 프로젝트 소스에서 **`dotnet publish`를 자동 실행**해 `dist/win-x64`에 실행 파일과 의존 파일을 함께 게시하고 앱을 엽니다. 다른 PC로 소스만 복사한 경우에도 같은 CMD를 사용합니다. 정상 배포 파일이 이미 있으면 .NET 준비 후 재게시 없이 실행합니다.

자동 설치는 [Microsoft의 공식 설치 스크립트](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-install-script)로 .NET 10의 최신 정식 x64 SDK를 `%LOCALAPPDATA%\TerminalNotes\dotnet`에 설치하며, 다음 실행부터 재사용합니다. 설치된 SDK와 .NET 10 실행 환경이 이미 충분하면 다운로드하지 않습니다. SDK를 프로젝트에 포함하지 않으므로 다른 PC로 전송하는 프로젝트 크기는 늘어나지 않습니다. 새 CMD를 열 필요 없이 앱 실행과 게시에 준비된 .NET 환경을 사용합니다. 시스템 설치·전역 PATH·저장된 PowerShell 실행 정책은 변경하지 않습니다. 실행 정책이 전혀 설정되지 않은 PC에서는 시작 프로세스에만 RemoteSigned를 적용하며, 사용자가 지정한 정책이나 그룹 정책이 있으면 그대로 따릅니다. 최초 설치에는 Microsoft 다운로드 서버, 게시에는 NuGet 패키지 소스에 접근할 수 있어야 합니다. 설치나 게시에 실패하면 오류를 표시하고 앱을 실행하지 않습니다.

자동 게시 성공 후에는 `Clean-BuildArtifacts.ps1 -Apply`로 빌드 임시 파일을 정리합니다. 정리에 실패하면 경고를 표시하고 게시된 앱은 실행합니다. 실행 중인 이전 버전은 유지하며, **프로그램 종료**로 완전히 종료한 뒤 실행기를 다시 열면 새 버전을 사용합니다. Windows 10 1809 이상 또는 Windows 11, .NET 10 Desktop Runtime이 필요하며 시작 시 Windows용 OpenCode 설치를 확인합니다. 터미널은 Windows 기본 환경에서 실행하며 WSL을 검사하거나 실행하지 않습니다. 레거시 화면을 선택할 때에는 WebView2 Runtime이 필요합니다.

창은 현재 모니터의 작업표시줄을 제외한 영역에 맞춰 열립니다. 저장된 크기가 화면보다 크면 자동으로 줄이며, 최대화할 때도 작업표시줄 위에 하단이 표시됩니다.

최초 실행은 Windows용 OpenCode 확인 → 작업 폴더·Auto Mode 설정 순서입니다. 일반 모드는 이 작업 폴더를 바로 사용하며 왼쪽 목록에서 태스크를 선택할 수도 있습니다. 기본 작업 폴더는 `C:\opencode`이며 `--workspace "프로젝트 경로"`도 지원합니다. Auto Mode는 OpenCode의 파일 수정·명령 실행 승인 설정입니다. 설정 변경은 기존 터미널을 재시작하지 않습니다.

작업 설정 창은 넓은 기본 크기로 열리고 현재 모니터의 사용 가능한 영역에 맞춰 조절됩니다. 작은 화면에서는 설정 내용을 스크롤할 수 있으며 하단 버튼은 계속 표시됩니다. 지침의 제목과 편집 버튼은 **전역 지침**·**플랜메이커 지침**으로 통일합니다.

앱 재실행은 이미 열린 창을 복원합니다. X/Alt+F4는 별도 알림 없이 트레이로 숨기고 세션을 유지합니다. 완전히 종료하려면 트레이나 세션 메뉴의 **프로그램 종료**를 사용합니다. 완전 종료 시 앱 안에서 시작한 OpenCode 서버와 bun 등 그 하위 프로세스도 함께 정리합니다. **CMD 이어가기**로 넘긴 외부 터미널은 별도로 유지됩니다. 완전 종료 후에는 프로젝트를 다시 선택하며 저장한 문서는 보존됩니다. 미전송 초안은 메모리에만 유지됩니다.

## 글꼴

화면 글꼴은 앱에 내장한 Pretendard(정적 Regular·Medium·SemiBold·Bold)를 사용하므로 PC에 따로 설치하지 않아도 같은 모양으로 표시됩니다. Pretendard는 SIL Open Font License 1.1로 배포되며 라이선스 전문은 `Assets/PRETENDARD-LICENSE.txt`에 있습니다. 터미널 본문 글꼴은 별도로 유지합니다.

## 일별 오류 기록과 버전

프로그램 이름 오른쪽에는 실행 중인 파일의 실제 버전에서 앞의 세 구간을 읽어 `v1.0.129` 형식으로 표시합니다. 일별 로그에는 전체 파일 버전과 빌드 식별자를 기록합니다. 독립 프로젝트의 `TerminalNotes.csproj` 버전도 확정된 배포 버전과 맞춰 관리하며, 화면에 버전 숫자를 직접 고정하지 않습니다.

시작·종료, 처리되지 않은 예외, 터미널 종료·연결 오류, 화면 응답 정지와 자원 경고는 `%LOCALAPPDATA%\TerminalNotes\diagnostics\daily`에 날짜별 JSONL로 저장합니다. **설정 → 로그·내보내기…**에서 로그 폴더를 열거나 최근 7일의 일별 로그를 ZIP으로 저장해 전달할 수 있습니다. 저장 실패도 이 창에서 확인할 수 있습니다. 일별 로그는 최대 14일, 총 64 MiB 이내로 관리하며 대화·명령 입력·플랜 원문·인증 정보는 복사하지 않습니다.

정상 종료 기록 없이 끝난 실행은 다음 시작 때 마지막 확인 시각과 함께 남깁니다. 강제 종료·전원 차단·Windows 재부팅의 정확한 발생 시각이나 원인을 앱 로그만으로 확정하지는 않습니다. 기존 자동 진행·화면 멈춤·자원 진단 로그와 분석 기능도 유지합니다.

## 공지

버전 오른쪽의 **공지**에서 내용을 확인합니다. 아직 읽지 않은 내용이 있으면 금색 원이 표시되고, 확인한 뒤 내용이 바뀌면 다시 표시됩니다. 읽음 상태는 Windows 사용자별로 보관합니다.

공지는 프로젝트 루트의 `공지.md`로 관리합니다. 프로젝트 없이 배포본만 사용하는 경우 실행 파일 옆의 `공지.md`를 사용합니다. `.env`의 `MASTER_USERS`(마스터 계정, 쉼표로 여러 명, 기본 `test_01`·`test_07`·`test_08`)에 적은 실제 Windows 계정에게만 앱의 **추가**·**수정** 기능을 제공하고 저장 시에도 계정을 확인합니다. 다른 계정은 읽기만 가능합니다. 파일을 직접 편집할 수 있는 권한은 Windows 폴더·파일 권한을 따릅니다.

공지 파일을 각 PC에 배포하거나 같은 파일 위치를 사용해야 같은 내용을 볼 수 있습니다. 이 기능이 별도 온라인 서버에 공지를 전송하지는 않습니다. 공지 파일은 UTF-8 기준 256 KiB, 2,048줄까지 지원하며 앱 업데이트와 임시 파일 정리에서 덮어쓰거나 삭제하지 않습니다.

## 자동 진행(loop) 진단

태스크를 우클릭하고 **자동 진행 진단 로그 열기**를 선택하면 중단·대기·복구 이유를 확인할 수 있습니다. 기본 로그는 `%LOCALAPPDATA%\TerminalNotes\settings.json.automation-diagnostics.jsonl`이며, 다른 설정 파일로 실행하면 해당 설정 파일 경로 뒤에 `.automation-diagnostics.jsonl`이 붙습니다.

로그에는 발생 시각, 프로젝트, 현재 세션·요청 식별자, 복구 단계, 오류 코드·종류와 마지막 실제 진행 시각을 기록합니다. 상태 변화와 활성 작업의 주기적인 점검을 남기며 요청 본문·플랜 내용은 기록하지 않습니다. 일시적인 점검 예외는 현재 작업을 유지하며 다시 확인하고, 전송 결과가 불확실한 요청은 중복 전송하지 않습니다.

사용자 확인이 필요한 상태는 태스크 상태 설명과 툴팁에 표시하고, 알림이 허용되어 있으면 **Loop 확인 필요** 트레이 알림을 띄웁니다. 알림은 실행을 막지 않으며 알림을 꺼도 로그와 상태 설명은 유지됩니다.

고급 모드에서 플랜을 사용하는 경우 왼쪽의 **new**로 작업 폴더를 만듭니다. 빈 터미널 칸을 클릭하면 기존 태스크 목록에서 선택할 수 있습니다. **플랜에 추가**에 원하는 작업을 적고 입력창 아래의 **저장** 또는 **실행**을 누릅니다. 저장만 하면 모델로 전송하지 않습니다.

화면 전체가 **15초 이상 응답하지 않으면** UI 바깥의 감시가 `.ui-diagnostics.jsonl`에 시각, 마지막 터미널 처리 단계와 프로세스 식별자를 기록합니다. 태스크 우클릭 → **화면 멈춤 진단 로그 열기**로 확인합니다. 화면이 다시 응답하면 복구 기록과 상태 안내를 남깁니다. 이 로그는 응답 정지를 관측한 기록이며 원인을 자동으로 확정하거나 앱 전체를 강제 종료하지 않습니다. 터미널 크기 변경과 종료 정리는 각 터미널의 백그라운드 작업에서 처리하여 Windows의 응답 대기가 공통 UI를 직접 막지 않도록 했습니다.

여러 터미널이 동시에 출력할 때에도 클릭과 키보드 입력이 처리될 수 있도록 출력 처리를 작은 묶음으로 나누고 입력보다 낮은 우선순위로 예약합니다. OpenCode의 연속 상태 알림은 터미널별 최신 상태로 합쳐 화면을 갱신합니다. 출력 기록과 실제 세션 상태는 유지하며, 이 처리는 이미 실행 중인 프로세스의 CPU·메모리를 강제로 제한하는 기능은 아닙니다.

같은 터미널 버전과 스크롤 위치의 화면 데이터, 글자 크기 측정 결과, 고정 색상 브러시는 재사용합니다. 세션 선택 목록도 항목을 매번 새로 만들지 않고 바뀐 내용만 반영합니다. 출력과 입력의 처리 주기, 동시 실행 수, 글자 품질은 유지하면서 중복 할당과 화면 갱신 비용을 줄입니다. 외부 OpenCode나 해당 작업이 실행한 프로그램의 자원 사용량까지 제한하는 기능은 아닙니다.

TUI 시작 중 일시적인 연결 오류에는 안전한 상태 조회와 기존 세션 선택을 제한된 횟수만큼 재시도합니다. 진행 중인 작업이나 Loop의 다음 개선 점검이 남아 있으면 화면 연결의 종료 코드와 관계없이 간격을 늘려 같은 서버·세션에 다시 연결하며, 횟수 제한을 두지 않습니다. 작업이 없는 화면의 비정상 종료에는 최대 두 번 다시 연결하고, 계속 실패하면 해당 터미널의 **재연결** 버튼을 사용할 수 있습니다. 화면 재연결은 작업 요청을 다시 보내거나 새 대화를 만들지 않습니다. 중단·×를 누르거나 예약된 재연결의 작업·입력 상태가 바뀌면 자동 재연결을 취소합니다. 화면에 표시할 문자가 도착하고 프로세스가 살아 있는 상태는 **TUI 화면 실행 중**으로 표시하며, 실제 대화 화면의 연결 완료를 보증하는 상태는 아닙니다. 초기 커서·제목 등 제어 신호만으로는 화면 준비를 인정하지 않습니다. 플랜메이커 질문 중 화면 프로세스가 끊어지면 무한 대기하지 않고 초안을 유지한 채 재시도를 안내합니다. 실패 단계와 재시도·종료 코드는 진단 로그에 남깁니다.

**작업 설정(톱니바퀴) → 로그 분석…**에서 현재 설정의 화면 멈춤·자동 진행 로그를 분석합니다. **파일 불러오기…**로 다른 PC에서 가져온 JSONL 로그도 선택할 수 있습니다. 응답 지연 시간, 복구 여부, 터미널 오류와 최근 처리 단계를 요약하며 확인된 기록과 추가 확인이 필요한 원인을 구분합니다. 큰 로그는 최근 일부를 읽었다고 표시하고, 기록 중인 파일이나 손상된 줄은 가능한 범위에서 분석합니다. **요약 복사**는 분석 결과만 복사하며 로그를 외부로 전송하지 않습니다. 앱이 멈춘 상태에서는 다시 실행한 뒤 남은 로그를 분석하세요.

프로그램 실행 중에는 5초마다 시스템 메모리 사용률과 TerminalNotes 및 확인된 하위 프로세스의 메모리를 백그라운드에서 기록합니다. 설정 파일 경로 뒤에 `.resource-diagnostics.jsonl`이 붙으며, 2 MiB에 도달하면 이전 파일 하나를 `.1`로 보관합니다. 로그 분석에서 실행 파일명·표시 이름·프로세스 ID와 메모리 사용량을 확인할 수 있습니다. 명령줄과 대화 내용은 수집하지 않으며 프로세스 목록과 기록 크기는 제한됩니다. 수집할 수 없거나 일부만 기록한 경우에는 부분 결과로 표시합니다. 작업 집합에는 공유 메모리가 포함될 수 있고, 높은 사용률만으로 메모리 누수나 멈춤 원인을 확정하지 않습니다. 이 기록이 없는 이전 버전의 로그로는 당시 메모리 사용량을 확인할 수 없습니다.

**메모리 보호:** 태스크에서 실행되는 모든 프로그램(OpenCode와 에이전트가 띄운 Python·Node·개발 서버, 터미널)은 하나의 메모리 한도 아래에서 돕니다. 한도는 5초마다 PC의 여유 메모리에 맞춰 바뀌고(Windows와 다른 프로그램 몫으로 RAM의 8% 또는 768MB 이상을 남김), 프로그램 하나는 RAM의 절반까지 씁니다. 한도를 넘으려는 프로그램은 PC 전체를 멈추게 하는 대신 그 프로그램만 메모리 부족 오류를 내고, 앱이 어느 태스크의 어떤 프로그램인지 알립니다. 에이전트는 지침에 따라 데이터를 나눠 다시 처리합니다. OpenCode 터미널은 PowerShell을 거치지 않고 opencode.exe를 바로 실행합니다(터미널당 약 50MB 절약).

자원 대기는 시스템 전체 메모리·CPU 사용량을 기준으로 하므로 보안 프로그램의 부하도 반영합니다. 다만 앱의 하위 프로세스가 아닌 외부 보안 센서의 개별 메모리나 프로세스 안에 로드된 보안 모듈별 할당량은 수집하지 않습니다. 따라서 이 기록만으로 Cybereason ActiveProbe나 MiniStackScan을 멈춤의 원인으로 확정할 수 없으며, 발생 시각이 일치하는 보안 센서 로그와 함께 확인해야 합니다.

## 전역 지침과 프로젝트 플랜

제목 표시줄의 **작업 설정(톱니바퀴) → 전역 지침 편집**에서 공통 Markdown을 수정·추가·저장합니다. 긴 문장은 편집기 너비에 맞춰 자동으로 줄바꿈되며, 하단 상태표시줄에서 편집 중·저장 완료·저장 충돌을 구분합니다. 상단의 최소화·최대화·닫기 버튼으로 창을 조절할 수 있습니다. 기본 경로는 `%LOCALAPPDATA%\TerminalNotes\Instructions\global-agent-instructions.md`입니다. 일반 Markdown 편집기로 수정해도 됩니다.

제목 표시줄의 **스킬**(스킬스토어, 작업 설정 톱니바퀴 바로 왼쪽, `.env`의 `MASTER_USERS` 마스터 계정에만 보임)에서는 지침을 OpenCode 스킬로 공유하고 받아 씁니다. 스킬은 한 줄에 세 장씩 카드로 보입니다(제목, 짧은 설명, 왼쪽 아래 금색의 날짜 · 작성자, 오른쪽 위 별, 스위치). 날짜는 첫 버전이면 만든 날, 새 버전이 있으면 마지막으로 고친 날입니다. 설명이 따로 없으면 지침의 첫 줄이 설명 자리에 보입니다. 켜 둔(적용된) 스킬은 위쪽 **적용됨** 구역에 따로 모이고 나머지는 아래 **적용 안 됨** 구역에 보이며(구역 안에서는 별을 누른 스킬이 맨 앞), 위의 검색 칸과 카테고리 탭(가나다순, 카테고리 없이 올린 스킬은 맨 끝 **기타**)으로 좁히며, 제목 표시줄의 새로고침 아이콘으로 다시 불러옵니다. 카드의 스위치를 켜면 바로 반영되고, 끄면 빠집니다. 적용한 스킬은 OpenCode 전역 스킬 폴더(`~/.config/opencode/skills`)에 들어가고, 스킬을 켜거나 끄거나 고치면(다른 프로그램이 그 폴더를 고쳐도) 이미 열린 OpenCode 터미널에도 바로 반영됩니다. OpenCode는 스킬을 한 번 읽어 두므로 앱이 각 터미널의 OpenCode를 쉬는 순간 다시 읽게 하며(대화 기록은 그대로), 작업 중인 터미널은 그 작업이 끝나는 대로 반영합니다. **+ 스킬 공유**에서 제목과 카테고리(있는 것을 ⌄로 고르거나 새로 씀)를 쓰고, **텍스트**(기본) 탭에 지침을 쓰거나 붙여 넣거나, **파일** 탭에서 지침 파일(.md·.txt, OpenCode SKILL.md나 그 폴더)을 끌어 놓거나 고르거나, **깃허브** 탭에 GitHub Enterprise(또는 github.com)의 SKILL.md 링크를 넣으면 스토어에 올라갑니다. 깃허브 링크로 올린 스킬은 중계 서버가 10분마다 그 파일을 확인해 바뀌면 새 버전으로 올리고, 적용한 PC는 스토어를 열 때 그 버전을 받습니다. **나만 보기**를 켜면 그 스킬은 올린 사람에게만 보입니다. 고른 탭의 내용이 올라가고, 첫 줄의 `# 제목`은 제목 칸을 채웁니다. 스토어에는 `제목-사용자 이름`(이 PC의 Windows 계정)으로 보입니다. 나머지는 스킬마다 **⋯** 메뉴(오른쪽 클릭도 같음)에 있습니다: **내용 보기**, **버전 기록**, **내 지침**, 처음 올린 사람에게 보이는 **수정**·**삭제**(마스터 계정은 작성자와 상관없이 모든 스킬을 수정·삭제하며, 그렇게 올린 새 버전도 원래 작성자의 스킬로 남음). 카드 오른쪽 위 별 바로 왼쪽의 배지가 최신 버전(`v3`)입니다. 태스크마다 쓸 스킬은 **태스크 우클릭 → 스킬…**에서 켜고 끕니다: 그 태스크 폴더의 `.opencode\skills`에 들어가 그 태스크에서만 쓰이고, 스킬스토어에서 켠 스킬은 모든 태스크에 쓰이는 전역 스킬입니다. 전역 스킬도 이 창에서 끄면 그 태스크에서만 빠집니다(다른 태스크와 전역 설정은 그대로, 새로 여는 OpenCode 터미널부터). **수정**에서는 고친 파일을 끌어 놓거나 텍스트 탭(최신 버전의 지침이 채워져 있음)에서 고쳐 새 버전으로 올립니다. 새 버전 번호는 다음 번호로 채워지고 더 큰 번호로 바꿀 수 있으며(바뀐 점도 적음), 스토어에는 최신 버전만 보이고, 적용한 스킬에 새 버전이 나오면 **업데이트**가 보입니다. **버전 기록**에서는 버전별 기록과 내용을 보고, **비교**는 VS Code의 비교 화면처럼 왼쪽에 바로 이전 버전, 오른쪽에 그 버전을 나란히 보여 줍니다(양쪽 줄 번호, 바뀐 줄과 그 안의 바뀐 글자 강조, 한쪽에만 있는 줄의 반대편은 빗금, 오른쪽 끝의 변경 위치 표시, ↑ ↓ 또는 Alt+F5·Shift+Alt+F5로 변경 사이 이동, 창이 좁으면 위아래로). 확인한 뒤 원하는 버전을 적용합니다. **내 지침**에서는 스토어 버전은 그대로 두고 이 PC에서만 쓸 지침을 덧붙입니다(위 내용과 다르면 내 지침을 따름). 새 버전이나 다른 버전을 적용해도, 해제했다가 다시 적용해도 내 지침은 그대로 남습니다. SKILL.md를 직접 고쳐도 사라지지 않습니다. 표시 줄 아래만 고치면 내 지침으로, 위의 스토어 부분을 고치면 직접 관리로 받아들이고, 그동안 스토어 새 버전은 그 스킬을 바꾸지 않습니다. 그런 스킬의 **내 지침**에만 **스토어 + 내 지침 | 전부 직접 관리** 탭이 보여, 고친 전체 글을 계속 고치거나 스토어 버전으로 돌아갈 수 있습니다. 직접 만든 같은 이름의 스킬은 바꾸거나 지우지 않습니다. 스토어는 문제 보내기와 같은 중계 서버(`relay\relay.py`)를 씁니다. 서버 PC에는 `out\TerminalNotesRelay` 폴더(`build\Publish-Release.ps1`이 함께 만듦)를 통째로 복사하고 **서버 시작.cmd**를 실행하면 됩니다(자동 실행 등록·방화벽·지금 시작, 끄기는 **서버 중지.cmd**, 자세한 내용은 `relay\README.md`). 앱 설정은 저장소 맨 위 `.env` 하나뿐이고, 중계 서버는 `.env`를 쓰지 않고 `relay.py` 맨 위 SETTINGS에서 설정합니다.

스킬은 계정과 상관없이 누구나 작성하고 자기 스킬을 수정·삭제합니다. 작성자는 카드의 ⋯ 메뉴(**비공개로 바꾸기**·**공개로 바꾸기**)로 언제든 공개 범위를 바꿉니다(새 버전이 생기지 않음). 비공개 스킬은 작성자에게만 보입니다. 다른 사용자가 이미 적용했더라도 그 PC에서 해제되어 쓸 수 없게 됩니다(서버 부담을 줄이려고 주기적으로 확인하지 않고, 앱을 켤 때 한 번과 제목 표시줄 **스킬**이나 태스크의 **스킬…** 창을 열 때 확인합니다. 해제하면 열린 터미널에서도 바로 빠집니다). 다시 공개하면 직접 켜서 적용합니다. 삭제한 스킬은 적용한 PC에 그대로 남습니다. 지금은 `.env`의 `MASTER_USERS`만 **스킬** 버튼을 봅니다. 모두에게 열 때는 `MASTER_USERS=dm,*`처럼 `*`를 더하면 되고, 다른 마스터 권한(공지, 모든 스킬 수정·삭제, Loop)은 적힌 계정에만 남습니다.

스토어 내용은 앱이 아니라 중계 서버의 데이터 폴더(2.12부터 `C:\ProgramData\TerminalNotesRelayData`, relay.py 폴더와 따로)에 있어서, 앱을 릴리즈하거나 서버의 relay.py 폴더를 새로 복사·삭제해도, 서버를 다른 계정이나 다른 Python으로 돌려도 사라지지 않습니다. 예전 위치(`%LOCALAPPDATA%\TerminalNotesRelay`, relay.py 옆)의 스토어는 서버가 시작할 때 복사해 오고, 스킬·공지는 하루 한 번 `backups`에 ZIP으로 백업되어 `python relay.py --restore-backup`으로 되살리거나 새 서버 PC로 옮길 수 있습니다. 적용한 스킬은 각 PC의 `~/.config/opencode/skills`에 있고 앱 업데이트가 건드리지 않습니다.

전역 지침 기본값의 **스킬과 플러그인** 절은 에이전트가 작업을 시작할 때 스킬 목록을 확인하고 맞는 스킬을 먼저 따르도록 합니다. 지침을 직접 고쳐 쓰는 PC는 자동으로 바뀌지 않으니 이 절을 직접 넣습니다.

공지 작성 계정이 공지 창에서 저장한 공지는 같은 중계 서버를 통해 모든 사용자에게 보입니다. 다른 PC는 앱을 켤 때, 창이 보이는 동안 1분마다, 창을 다시 볼 때 새 공지를 받아 읽지 않음 표시를 띄웁니다. 공지 창 위쪽 한 줄이 공유 상태를 알려 줍니다(작성 계정에게는 지금 이 공지를 받은 PC 수). 서버에 연결하지 못하면 이유와 함께 마지막으로 받은 공지를 보여 줍니다. 다른 PC가 서버에 닿으려면 서버 PC의 방화벽을 한 번 열어야 합니다(`python relay\relay.py --allow-firewall`).

`.env`의 `AGENT_SELECTION=yes`면 태스크 행의 에이전트 아이콘을 눌러(또는 우클릭 → 에이전트) 태스크마다 OpenCode·Codex·Claude Code 중 하나를 고릅니다. 기본은 OpenCode이고, 고른 에이전트는 그 태스크의 다음 터미널부터 쓰입니다. Loop와 플랜메이커는 OpenCode에서만 동작합니다. `no`(기본)면 아이콘과 메뉴가 숨겨지고 모든 태스크가 OpenCode로 실행됩니다. 태스크 순서는 행을 끌어 다른 태스크 위·아래에 놓아 바꾸며, 바꾼 순서는 저장됩니다.

**작업 설정 → 플랜메이커 지침 편집**에서는 질문 방식과 플랜 정리 기준을 수정·저장합니다. 저장한 지침은 새로 시작하는 플랜메이커 대화부터 적용하며, 진행 중인 대화에는 처음 시작할 때의 지침을 유지합니다. 기본 경로는 `%LOCALAPPDATA%\TerminalNotes\Instructions\plan-maker-instructions.md`입니다. 외부 편집과 충돌하면 덮어쓰지 않고 알려줍니다. 지침을 바꿔도 플랜메이커가 코딩을 시작하거나 플랜을 자동 저장하지 않으며, 사용자가 메인 화면에서 저장 또는 실행을 눌러 확정합니다.

직접 수정한 지침을 유지하며, 교체가 승인된 이전 지침과 내용이 같은 파일은 원본 백업 후 갱신합니다. 기본 지침 원문은 `global-agent-instructions.md`에서 확인할 수 있습니다. 편집 이후 외부에서 내용이 바뀌면 저장을 거부하고 초안을 유지합니다. 새 터미널/CMD 실행부터 공통 파일 경로가 연결되고, 연결된 세션은 다음 모델 요청에서 파일을 읽습니다. 사용자 OpenCode 설정이나 프로젝트 AGENTS.md는 수정하지 않습니다.

새 태스크(프로젝트)를 만들 때는 이름과 **기본 목표**만 입력하며, 새 플랜에는 `## 목표` 아래 그 목표만 들어갑니다(비우면 목표 제목만). 요구사항·조건·완료 기준은 나중에 플랜메이커나 플랜 입력으로 더합니다. 기존에 작성한 플랜은 자동으로 바꾸지 않습니다.

프로젝트별 기준 문서는 기존과 같은 `<프로젝트>/terminal-notes/plan.md`입니다. 프로젝트를 선택하면 해당 파일을 읽고, 문서 전체를 직접 편집할 수 있습니다. **저장**은 문서와 추가 입력을 저장하고, **실행**은 저장 후 같은 프로젝트의 터미널로 요청을 보냅니다. 추가 입력이 없으면 저장한 플랜 전체를 실행합니다. 외부 수정과 충돌하면 초안을 덮어쓰지 않습니다.

## 플랜 입력

왼쪽 태스크 목록 아래에는 선택한 프로젝트의 플랜 문서를 항상 표시하고, 바로 아래의 **플랜에 추가** 입력창에서 요청을 작성합니다. 왼쪽 패널의 기본 폭은 360 DIP이며, 태스크와 플랜은 연결되는 회색 계열로 구성합니다. 플랜 문서는 중간 명도의 회색, 새 요청 입력창은 한 단계 밝은 회색으로 구분하고 밝은 글씨와 테두리로 가독성을 높입니다. 입력 중에는 파란 테두리로 강조하고, 빈 편집창의 안내 문구는 입력을 시작하면 사라집니다. **플랜메이커**는 플랜 영역 우상단에 배치합니다. **플랜에 추가** 입력창은 세 줄 높이로 표시하고, 남는 높이는 위쪽 플랜 문서에 배정합니다. 목록과 플랜 영역 사이의 경계로 높이를 조절하면 플랜 문서가 늘어나고, **저장·실행** 버튼은 플랜 영역 하단에 고정됩니다. 긴 내용은 각 편집창 안에서 스크롤합니다. 태스크 화면에서는 플랜 문서만 따로 접지 않습니다. 왼쪽 패널 전체를 접으면 목록과 플랜 영역을 함께 숨기며, 다시 펼치면 플랜도 표시합니다. 터미널 세션과 프로젝트별 입력 초안을 유지합니다. Ctrl+S는 저장, Ctrl+Enter는 실행입니다. 질문은 OpenCode 터미널에 직접 입력합니다. 저장이나 전송이 성공하면 완료를 표시하고 해당 입력을 비우며, 실패하거나 대기 중 새로 작성한 내용은 보존합니다.

**저장**은 기존 플랜 뒤에 입력한 원문만 추가하고 전송하지 않습니다. **실행**은 저장한 추가 요청을 같은 프로젝트의 터미널에 전달합니다. 시각이나 추가 요청 제목은 자동으로 넣지 않습니다. 저장에 실패하면 전송하지 않습니다. 전송에 실패해도 저장된 플랜과 입력 초안은 남으며, 반복 저장이나 같은 요청 재시도는 플랜에 중복 추가하지 않습니다. **전송**은 입력한 원문을 플랜에 추가하지 않고 그대로 보냅니다. 태스크 터미널이 실행 중이 아니면 ▷처럼 빈 칸에 터미널을 먼저 열고, 준비되면 보냅니다.

터미널이 작업 중이어도 새로 작성한 추가 요청을 **실행**하면 같은 세션으로 바로 전송합니다. 접수를 확인하면 전송 완료를 표시하고 해당 입력을 비웁니다. 기존 작업과 추가 요청의 처리 순서는 OpenCode가 관리하며, 전송 완료 표시는 AI 작업의 완료를 뜻하지 않습니다. 승인·질문 응답이 필요하거나 플랜메이커가 진행 중이면 화면의 안내를 먼저 처리합니다.

**플랜메이커**는 기존 태스크에서도 프로젝트를 선택하면 바로 열 수 있습니다. 추가 요청을 미리 적어도 되고, 입력 없이 열면 기존 플랜에서 추가·변경할 내용을 질문합니다. 플랜이 비어 있으면 만들고 싶은 목표부터 질문합니다. 별도 모달의 전용 OpenCode 터미널에서 AI가 요구사항과 구현 방향을 질문하며, 질문 화면에서 답합니다. 기존 코딩 터미널과 별도 세션을 사용하고 메인 터미널 칸을 차지하지 않습니다. 확인된 대화 내용은 선택했던 프로젝트의 플랜 초안에 누적하며, 기존 플랜을 보존합니다. 대화가 끝나면 모달을 닫고 초안을 확인한 뒤 **저장**으로 파일에 저장하거나 **실행**으로 저장하고 코딩을 시작합니다. 플랜메이커 자체는 초안을 파일에 저장하거나 코딩을 시작하지 않습니다. 대화 중 플랜 파일이나 편집 초안이 바뀌면 덮어쓰지 않고 알려줍니다. 중단·오류 시 원래 입력과 이미 반영한 초안을 유지하며, 정상 완료 시에는 대화 중 새로 수정하지 않은 원래 입력만 비웁니다. 모달을 닫으면 플랜메이커 전용 세션과 하위 프로세스를 정리합니다. 기존 코딩 터미널은 계속 실행되며 새 전용 터미널에는 같은 자원 대기 규칙을 적용합니다. 플랜메이커의 자원 대기 화면에서 **이번만 실행**을 누르면 해당 시작 한 번에만 자원 사용량 제한을 우회합니다. 다른 터미널과 이후 재시작에는 기본 제한을 유지하며, 동시 시작 방지와 시작 간격은 그대로 적용합니다.

AI가 초안을 작성한 뒤에도 같은 대화에서 부족한 요구사항을 한 가지씩 추가로 질문합니다. 충분히 구체화되면 **플랜으로 돌아가기**를 누르세요. 질문을 마치고 답변 반영이 끝나면 미저장 플랜 초안으로 자동으로 돌아갑니다. 저장과 실행은 메인 플랜에서 선택합니다. AI가 질문 없이 응답을 끝내는 경우 자동 재요청을 제한하고 **질문 계속**으로 이어갈 수 있게 표시합니다.

확인된 요구사항은 같은 상위 제목과 카테고리 아래에 모읍니다. 같은 내용의 재전송은 중복 추가하지 않고, 새 조건만 해당 항목에 반영합니다. 기존 요구사항의 수치·예외·경로·코드 등 구체적인 내용은 요약하거나 삭제하지 않습니다. 재시도에서도 앞서 확인한 내용을 유지하며, 파일 반영은 사용자가 **저장** 또는 **실행**을 눌렀을 때, 코딩 시작은 **실행**을 눌렀을 때만 진행합니다.

플랜메이커의 **Auto Recommand**를 켜면 현재 질문과 이후 질문에 추천 답변을 자동으로 선택합니다. 처음에는 꺼져 있으며, 같은 버튼을 다시 눌러 해제합니다. 버튼 이름은 유지하고 상태 표시로 켜짐·꺼짐과 진행 단계를 구분합니다. 첫 질문부터 모든 후속 질문에 추천 선택지 하나와 이유를 포함하도록 요청합니다. 추천 표시나 이유가 빠졌거나 추천이 모호하면, 같은 설정 모델이 현재 질문과 선택지를 별도의 도구 사용 없는 세션에서 검토해 추천을 보완한 뒤 계속 진행합니다. 추천 표시는 라벨의 '(Recommended)'·'(추천)'·'(추천: 이유)'·'추천: A'·'A - 추천', 설명 앞의 '(추천)', 질문 문장의 'A를 추천합니다'도 인식합니다. 이 검토는 최대 90초로 제한하며, 실패하면 원인과 직접 답변 또는 다시 시도 안내를 표시합니다. 사용자만 답할 수 있는 질문이면 그 질문만 직접 답변을 기다리고, 다음 질문부터 다시 자동으로 선택합니다. 확인되지 않은 사실을 지어내거나 실제 권한 승인을 자동 수락하지 않습니다. 시스템에서 애니메이션을 끈 경우에도 상태 문구는 유지합니다. 질문을 마치거나 다시 시도하면 Auto Recommand도 종료합니다. 질문 종료 시점과 플랜의 저장·실행은 사용자가 선택합니다.

AI가 이전 항목이나 전체 플랜을 다시 보내도 이미 반영한 같은 항목은 중복으로 추가하지 않습니다. 기존 플랜 원문과 새로운 요구사항을 보존하며, 서로 다른 절에 있는 같은 문장이나 코드 예제의 반복 줄은 구분합니다. 이 처리는 대화 중 갱신, 오류 후 재시도, 기존 플랜에 초안을 합칠 때 모두 적용합니다.

플랜메이커는 원래 모델명이나 화면 표시 이름을 추측하지 않고 OpenCode에 설정된 `provider/model` 식별자를 그대로 보냅니다. 전용 세션의 이전 사용자 요청에 명시된 모델, 공통 `model` 설정, `plan` 에이전트의 명시적 모델 설정 순서로 확인하며, 대화가 시작되면 후속 질문에도 같은 식별자를 사용합니다. 명시된 모델이 없으면 모델 지정을 생략하여 OpenCode의 기본 선택을 따릅니다. 이후 정확히 같은 플랜 요청의 사용자 메시지에서 선택된 모델 식별자를 확인하면 후속 질문에도 유지합니다. 명시된 설정 형식이 잘못되면 요청 전에 안내합니다. 다른 터미널에서 아직 요청에 사용하지 않은 모델 선택은 자동으로 가져오지 않습니다.

플랜메이커 모달은 왼쪽에 플랜 초안, 오른쪽에 질문·답변 터미널을 표시하며 경계선을 드래그해 폭을 조절합니다. 상단에는 현재 단계와 상태 설명, 앱 디자인에 맞춘 최소화·최대화·닫기 버튼을 표시합니다. 오류가 나면 초안을 유지하고 **다시 시도**를 제공합니다. 재시도는 이전 전용 터미널을 정리한 뒤 새 연결에서 OpenCode 설정을 다시 읽으며, 제공자나 모델을 임의로 바꾸지 않습니다. 무료 모델의 사용 제한은 연결 오류와 구분해 표시합니다. 제공자의 요청 거부는 터미널 연결이 정상이어도 발생할 수 있습니다. 표시된 오류와 OpenCode의 모델·인증 상태를 확인하고 다시 시도하세요. 제공자와 권한 설정의 호환성 문제일 수도 있으며, 앱에서 모델을 자동으로 변경하지 않습니다.

기존의 모든 터미널 입력 수집 플러그인은 새 실행과 CMD에 추가하지 않습니다. 과거 `terminal-inputs.md`와 실행 기록은 삭제하지 않습니다. 터미널에 직접 입력한 내용은 플랜에 자동 복사되지 않습니다. OpenCode 자체 세션 기록과 사용자가 별도로 설정한 기록 기능은 OpenCode 설정을 따릅니다.

## 싱글 터미널과 분할

지휘·검토·구현 역할 팀 대신 프로젝트마다 하나의 터미널을 재사용합니다. 과거 멀티 설정으로 역할 팀을 다시 생성하지 않으며, 예전 Running/Scheduled 역할 실행은 중단 상태로 보존합니다. 과거 기록 때문에 모델 작업을 자동 재개하지 않습니다.

상단의 **분할** 버튼(지금 배치를 작은 그림으로 표시)을 누르면 1~6칸 배치도가 그림으로 뜨고, 원하는 배치를 누르면 바로 바뀝니다(5칸은 위 3칸·아래 넓은 2칸). Esc로 닫습니다. 앱은 늘 1칸으로 시작합니다. 왼쪽 태스크 목록은 오른쪽 테두리 중앙의 화살표 버튼으로 접고 펼칩니다. 접으면 터미널 영역이 넓어지고, 다시 펼치면 조절했던 목록 폭으로 돌아옵니다. 접힘 상태와 폭은 재실행 후에도 유지됩니다. 카드는 **프로젝트 폴더 아이콘**, 이름, **시작/중단 버튼 하나**, **Loop 버튼 하나**를 한 줄로 표시합니다. 폴더 아이콘을 누르면 해당 카드의 프로젝트 폴더가 탐색기에서 열립니다. 버튼은 대기 중에는 ▶ 시작, 실행·준비 중에는 ■ 중단으로 바뀝니다. 터미널 열기 버튼은 제거했습니다. 태스크 카드를 원하는 터미널 칸으로 **드래그 앤 드롭**합니다. 각 터미널 칸은 편집 가능한 태스크명 한 줄과 터미널 본문을 표시합니다. 빈 칸의 **태스크 선택**을 클릭하면 태스크 목록만 표시합니다. 이 메뉴에는 새 프로젝트 만들기와 프로젝트 폴더 열기를 표시하지 않습니다. 취소하면 기존 배치를 유지합니다. 새 프로젝트를 추가하거나 폴더를 불러올 때 기존 터미널 배치를 유지하며, 비어 있는 가시 칸에만 자동 배치합니다. 칸이 모두 사용 중이면 태스크와 플랜만 추가·선택하고 원하는 칸으로 직접 드래그할 수 있습니다. 이미 숨겨진 칸에 배치된 프로젝트는 그 위치를 유지합니다. 위치 이동과 글자 선택은 마우스 해제·포커스 상실 시 드래그 상태를 정리하며, 복사할 선택 영역은 유지합니다.

이미 배치된 태스크 카드를 다른 칸에 놓으면 두 자리를 바꿉니다. 배치되지 않은 태스크를 채워진 칸에 놓으면 그 칸만 교체하며 기존 세션은 계속 유지합니다. 터미널 제목에는 **×** 하나만 표시하며 중복 닫기 버튼이나 칸 비우기 기능을 제공하지 않습니다. **×**나 태스크 우클릭의 **터미널 종료**를 누르면 해당 터미널과 그 하위 프로세스를 종료합니다. 프로젝트와 저장된 플랜은 남아 다시 시작할 수 있습니다. 작업 중단은 태스크의 ■ 또는 터미널 선택 메뉴에서 해당 세션을 우클릭해 선택합니다. 세션 종료도 터미널 메뉴에서 선택합니다. 분할 수를 줄여도 숨겨진 칸의 배치·세션·출력·초안이 유지되며 다시 늘리면 돌아옵니다. 왼쪽 플랜 패널은 선택한 프로젝트를 따릅니다.

태스크의 **시작**은 플랜이 없거나 비어 있어도 OpenCode 터미널을 엽니다. 이때 자동 요청을 보내지 않으며 터미널에 바로 입력할 수 있습니다. 플랜 영역에는 **플랜 없음 · 작업 시작 대기**를 표시해 OpenCode를 연 상태와 플랜 작업의 시작 여부를 안내합니다. 저장된 플랜에 내용이 있으면 같은 터미널로 플랜 실행 요청을 보냅니다. 플랜 요청은 화면 입력창의 로딩 시점에 의존하지 않고 해당 OpenCode 세션에 전달하며, 정확한 메시지의 접수를 조회해서 확인합니다. 연결 실패는 자동 재시도하고, 입력을 보내기 전에 터미널이 종료되거나 준비가 5분 이상 응답하지 않으면 해당 앱 소유 터미널을 자동 재시작합니다. 20초 이상 걸리는 단계는 경과 시간을 표시합니다. 응답이나 상태 알림을 놓친 경우 같은 메시지를 자동 재조회하며, 전송 결과가 불명확한 요청은 중복 제출하지 않습니다. 사용자의 중단·입력·승인 대기와 플랜 변경을 존중합니다. 플랜 없이 터미널을 열어도 플랜 원문을 바꾸거나 Loop 작업을 자동으로 시작하지 않습니다.
터미널 선택 메뉴에서 세션을 우클릭해 고르는 **저장된 plan.md 다시 읽기**는 해당 프로젝트의 저장된 `terminal-notes/plan.md`를 디스크에서 다시 읽어 실행합니다. 실행 중인 작업은 먼저 중단하고 같은 프로젝트 터미널을 재사용합니다. 편집 중인 미저장 플랜은 보존하며, 저장된 플랜이 없거나 비어 있으면 OpenCode 터미널만 열어 입력을 기다립니다.

태스크 상태에는 작업 상태와 OpenCode 상태 확인 여부를 함께 표시합니다. 실제 연결·상태 요청 중에는 **확인 중**, 연결된 상태에서 다음 응답을 지켜볼 때는 **상태 감시 중**, 연결이 끊겨 재시도를 기다릴 때는 **재연결 대기**, 확인 기능이 실행되지 않을 때는 **확인 안 함**으로 구분합니다. 상태 감시는 작업 진척이나 완료 검증을 뜻하지 않습니다. 승인·입력 대기와 오류도 카드에 표시합니다.

작업 중 오류가 발생하면 재시도 가능한 태스크와 터미널 상단에 **재시도** 버튼을 표시합니다. 사용자가 시작한 태스크는 별도 체크 없이 자동 진행을 적용합니다. 일시적인 연결·시간 초과·서버 오류를 1분·3분·이후 최대 10분 간격으로 다시 시도하며, 기다리는 이유와 남은 시간을 터미널에 표시합니다. **재시도**를 누르면 예약 시간을 기다리지 않고 현재 상태를 확인해 이어갑니다. 인증·설정 등 사용자 조치가 필요한 오류는 자동 반복하지 않으며, 원인을 해결한 뒤 수동으로 재시도합니다. OpenCode 자체가 재시도 중이거나 승인·질문 응답을 기다리면 그 처리를 우선합니다. 사용자 중단과 일시정지는 유지하며, 플랜메이커 전용 터미널에는 일반 작업용 자동 오류 복구·Loop를 적용하지 않습니다. 플랜메이커의 **Auto Recommand**는 별도의 질문 답변 기능입니다.

일시적인 요청 오류는 같은 세션에서 이어갑니다. 작업 요청 접수가 확인된 뒤 앱 소유 OpenCode 프로세스가 예기치 않게 종료되면, 해당 프로세스의 종료를 확인하고 원래 요청과 저장된 플랜을 보존해 다시 시작합니다. 재시작에도 자원 대기를 적용합니다. 현재 파일과 진행 내용을 먼저 확인하도록 하며, 이전 복구 안내문을 계속 누적하지 않습니다. 전송 결과가 불명확하면 같은 요청의 접수를 먼저 확인하고 새 요청을 중복 제출하지 않습니다. 중단·닫기·새 요청·플랜 변경은 이전 복구 예약에 우선하며, 다른 CMD나 외부 프로그램의 프로세스를 종료하지 않습니다.

여러 프로젝트가 동시에 동작할 때 복구 요청은 프로젝트별로 처리합니다. 한 프로젝트의 연결 확인이나 재시작이 오래 걸려도 다른 프로젝트의 오류 재시도·상태 확인까지 같은 잠금에서 기다리지 않도록 합니다. 같은 프로젝트의 복구는 여전히 중복 실행을 막으며, 새 프로세스의 시작에는 공통 자원 대기 규칙을 적용합니다. 이것은 앱 내부의 프로젝트 간 복구 대기 문제를 완화하는 것으로, 이미 실행 중인 외부 프로세스의 메모리 사용을 강제로 제한하지는 않습니다.

태스크/아카이브 목록과 프로젝트 제목 변경을 유지합니다. 우클릭으로 프로젝트 폴더 전체를 보관·복원하며, 실행·승인 대기는 먼저 중단해야 합니다. 코드·플랜·기록을 함께 이동하고 같은 이름의 폴더를 덮어쓰지 않습니다. 아카이브로 보내도 현재 탭을 유지하며, 성공하면 태스크 영역 위에 작은 알림을 잠깐 겹쳐 표시합니다. 알림은 약 2초 뒤 사라지고, 목록과 플랜의 공간이나 입력 포커스를 차지하지 않습니다. 태스크 화면의 플랜 문서는 왼쪽 **플랜에 추가** 입력창 위에 항상 표시합니다. 세로 경계의 화살표는 왼쪽 목록과 플랜 영역 전체를 접고 펼칩니다. 일반 노트 화면의 기존 패널 접기 동작은 유지합니다.

## Loop 1 / Loop 2

태스크 행의 Loop 버튼을 누르면 **Loop 1 · 플랜대로 개발**과 **Loop 2 · Auto Recommand까지 계속**(켜져 있으면 **Loop 끄기**도) 중에서 고릅니다. 켜진 Loop의 번호가 버튼의 우로보로스 옆에 작게 보입니다. 따로 고른 적이 없으면 Loop 2입니다.

**Loop 1**은 지금 플랜대로 개발하고 결과를 검토하며 반복합니다(플랜에 없는 기능은 더하지 않음). **Loop 2**(예전 Loop Full)는 작업 완료 후 별도의 플랜메이커에서 추천 질문에 답해 다음 개선 플랜을 만들고, 플랜의 `## Loop 모드` 구역에 따로 모아 저장한 뒤 다음 작업을 실행합니다(사용자가 쓴 내용과 섞지 않고, 이미 있는 줄은 다시 넣지 않습니다). 추천 선택지와 이유는 처음 질문부터 포함하며, 새 개선 항목이 없으면 대기 후 다시 점검합니다. 플랜 작성 중에는 진행 상태를 표시합니다. 사용자가 플랜을 편집하거나 중단한 경우, 실제 승인·질문이 남아 있는 경우에는 자동 저장·실행을 보류합니다. 두 모드는 동시에 켜지지 않으며 선택과 종료 예약을 프로젝트별로 기억합니다.

Loop는 종료 시간이 되거나 사용자가 멈출 때까지 스스로 멈추거나 꺼지지 않습니다. 추천 플랜메이커가 새 개선을 찾지 못하거나 다음 플랜 작성에 실패해도 그 회차는 결과를 검토·개선하는 요청으로 이어가고, 변화가 없으면 1·3·10분 간격으로만 늦춥니다. 모델 오류는 인증·권한·결제·잘못된 요청처럼 사람이 고쳐야 하는 경우를 빼고 계속 재시도합니다. 시작한 태스크가 멈추면 다시 실행합니다: 터미널이 닫히거나 실패했으면 30초, OpenCode가 쉬고 있는데 자동 진행이 멈췄으면 2분, 자동 진행이 붙어 있어도 20분 동안 아무 일이 없으면, OpenCode 상태를 5분 넘게 읽지 못하면(새 터미널로) 저장된 플랜으로 다시 실행하며, 진척 없이 되풀이되면 1·3·10분 간격을 둡니다. 에이전트가 묻는 질문에 5분 동안 답이 없으면 추천 답변(없으면 "알아서 판단해 진행")으로 답합니다. 메모리·CPU 과부하로는 최대 3분만 기다립니다(메모리가 거의 바닥난 경우만 더 기다림). 앱이나 Windows가 다시 시작되면 돌던 Loop를 이어 갑니다(사용자가 앱을 직접 종료한 경우는 제외). 사용자가 중단하거나 터미널을 닫은 태스크, 승인 답을 기다리는 태스크는 건드리지 않습니다.

태스크 메뉴의 **예약 실행**에서도 Loop 사용과 Loop 1 · Loop 2를 고를 수 있습니다(`MASTER_USERS` 마스터 계정에만 보이고, 플랜 모드에서는 보이지 않음). 고른 Loop는 예약 시간에 적용되고 카드의 예약 표시에 함께 보입니다.

각 프로젝트 카드의 **Loop 버튼**으로 켜고 끕니다. 반복 실행이 활성화되면 버튼에 색을 표시하며, 중단하면 색상을 해제합니다. 중단해도 저장된 Loop 선택은 유지됩니다. 설정은 해당 프로젝트에만 적용됩니다. 종료 시간이 필요하면 **카드 우클릭 → Loop 종료 예약**에서 설정합니다. Loop와 플랜메이커 Auto Recommand는 `.env`의 `MASTER_USERS`(마스터 계정, 쉼표로 여러 명, 기본 `test_01`·`test_07`·`test_08`)에 적은 Windows 계정에만 보입니다. 공지 작성·모든 스킬 수정·삭제·스킬스토어 보기도 같은 한 줄을 따릅니다. 빌드할 때 앱에 들어가므로 바꾼 뒤 다시 빌드합니다. 정한 시간에 태스크를 시작하려면 **카드 우클릭 → 예약 실행…**에서 날짜·시간과 Loop 사용 여부(필요하면 Loop 종료 시간)를 정합니다. 예약한 태스크에는 시계 표시와 시간이 보이며, 누르면 바로 변경·취소할 수 있습니다. 예약은 한 번 실행되면 지워지고, 앱이 꺼져 있어 지난 예약은 실행하지 않고 알립니다. 예약 시각은 버튼 툴팁과 우클릭 메뉴에 표시합니다. OpenCode에 설정된 기본 모델을 그대로 사용합니다. 에이전트에게 최신 플랜과 현재 코드를 대조하고 구체적인 남은 작업 한 가지를 구현·검증하도록 요청합니다. 요구사항별로 현재 코드·변경분·유효한 검증 결과부터 확인합니다. 이미 반영된 작업은 다시 구현하지 않도록 지시합니다. Loop에서는 완료 후에도 현재 프로젝트와 플랜 범위에서 누락·결함·검증·사용성을 다시 점검하고, 근거가 있는 개선 한 가지를 이어갑니다. 새로운 개선 근거가 없으면 불필요하게 파일을 바꾸지 않고 기다렸다가 다시 점검합니다. 사용자의 중단, 종료 예약, 승인·질문 대기를 우선합니다.

진행은 native 세션·작업 목록·도구 근거로 확인합니다. 답변이 길어지거나 busy 상태가 유지되는 것만으로 계속 진행했다고 보지 않습니다. 토큰 절약을 위한 재요청 횟수 제한을 두지 않습니다. 사용자가 시작한 태스크의 미완료 요청은 기본 자동 진행으로 1분·3분·이후 최대 10분의 대기 간격을 두고 계속 재개합니다. 일반 자동 진행은 처리할 일이 완료되면 멈추며, 별도로 켜는 Loop는 첫 개선 점검을 20초 뒤 예약하고 남은 대기 시간을 표시합니다. 작업 목록이 없거나 목록 이벤트를 놓쳤어도 현재 요청의 정상 종료 응답과 idle 상태가 확인되면 다음 개선 점검을 이어갑니다. 작업 목록에 진전이 없는 반복 점검은 1분·3분·최대 10분 간격으로 늦춰 불필요한 연속 요청을 줄입니다. 일시적인 조회 실패는 대기 후 재확인하며, 접수 여부가 불확실한 요청은 중복 전송하지 않습니다. 추가 목표는 플랜 입력으로 누적합니다. 자동화 장치만으로 생성 코드의 품질을 보장하지 않으며 실제 모델 검증은 별도로 필요합니다.

작업 목록 변경 알림이 누락되어도, 현재 요청에서 정상 완료한 작업 목록 기록과 서버의 최신 목록이 일치하면 남은 작업을 자동으로 이어갑니다. 이전 요청의 목록이나 확인되지 않은 변경만으로는 후속 요청을 보내지 않으며, 전송 직전에도 같은 근거를 다시 확인합니다.

현재 태스크 요청에서 로딩 표시(경과 시간)만 계속되고 응답·추론·도구 내용에 **3분간 변화가 없으면 정체 의심**으로 표시합니다. 같은 상태가 **5분간 유지되면 해당 요청을 취소**하고(Esc로 취소한 뒤 다시 보내는 것과 같음), 실제 idle 확인 후 최신 플랜을 기준으로 재요청합니다. 모델이 todo를 만들기 전에 멈춘 경우도 정확한 현재 사용자 요청을 확인한 뒤 복구합니다. 응답 내용 변화는 정체 시간을 초기화하지만, 실제 작업 진전 없는 재요청의 대기 간격은 초기화하지 않습니다. 긴 작업으로 최근 50개 메시지에 원래 요청이 빠지면, 응답들이 가리키는 동일한 요청 ID를 검증해 원문을 다시 조회합니다.

반복 실행 중 프로젝트 안의 앱 실행 명령 하나가 진행 없이 남아 있는 경우도 감지합니다. 지원하는 실행 명령과 현재 요청·도구가 정확히 일치하고 승인·질문·하위 작업이 없을 때, **15분 정체 후 해당 OpenCode 요청에 취소를 요청**합니다. 취소 접수만으로 실행한 프로그램의 종료를 단정하지 않으며, 새로운 idle 상태를 확인한 뒤 후속 요청을 보냅니다. 일반 빌드·테스트·임의 스크립트를 일괄 종료하지 않습니다. 새 실행 요청에는 미리보기 실행 시간을 제한하고 이번에 만든 프로세스를 정리하도록 안내합니다.

취소를 요청했는데도 **2분 더 동일한 busy 또는 대기 시각이 지난 retry 상태**이고 실행 중인 도구·하위 작업·승인 대기가 없으면, 해당 터미널의 앱 소유 프로세스 종료를 확인한 뒤 새 터미널에서 저장된 plan.md와 원래 요청으로 이어갑니다. 현재 파일을 먼저 확인해 이미 적용한 작업을 반복하지 않도록 지시합니다. 프로세스 재시작 횟수에도 제한을 두지 않습니다. 새 터미널이 다시 정체되면 같은 5분 정체·취소 후 2분 확인 절차를 거쳐 복구합니다. 원래 요청 전체를 보존하고 이전 복구 안내문을 반복 누적하지 않습니다. 저장·제어 작업과 잠시 겹치거나 요청 전송 전 시작에 실패하면 간격을 두고 다시 시도합니다. 전송 여부를 확인할 수 없으면 확인 필요 상태를 남깁니다. 기존 프로젝트 파일과 OpenCode 대화 기록은 삭제하지 않습니다. 사용자가 중단하거나 요청·플랜을 바꾸면 진행 중인 복구를 취소합니다.

Loop의 다음 개선 점검을 기다리거나 사용량 제한으로 대기하는 동안 OpenCode 프로세스가 종료되어도, 확인된 요청과 원래 작업을 보존해 복구합니다. 서버의 재시도 대기 시각은 프로세스를 다시 시작해도 유지하며 Loop 해제·종료 예약 이후 완료된 작업의 다음 점검을 재시작하지 않습니다. 실행 중인 작업의 터미널 화면 연결만 끊긴 경우에는 같은 세션의 화면을 다시 연결하며, 그 때문에 작업 요청을 재전송하지 않습니다.

상태 확인이 2분 넘게 끊겨도 그 이유만으로 진행 중인 요청을 폐기하지 않습니다. 연결이 돌아오면 같은 세션·요청·플랜인지 다시 확인하고 이어갑니다. 확인하지 못한 시간은 정체의 근거로 누적하지 않으며, 서버의 재시도 대기 시각과 사용자의 중단을 유지합니다. 전송 결과가 불명확한 요청은 접수 여부부터 확인합니다.

사용량 제한·일시적 오류가 나면 현재 요청을 보존하고 재시도합니다. 서버 과부하로 HTTP 503이 반환되거나 응답 스트림이 중간에 끊긴 경우에도 일부 응답만으로 완료 처리하지 않고 현재 요청의 상태를 확인해 이어갑니다. HTTP 429·503은 즉시 재시도 불가로 보고되어도 대기 후 다시 확인하며, 서버가 제공한 `Retry-After`나 사용량 초기화 시각보다 먼저 요청하지 않습니다. OpenCode의 native retry도 예정 시각까지 기다립니다. 예정 시각이 지났거나 예정 시각이 없는 retry가 실제 활동 없이 정체되면 현재 요청·승인·도구 상태를 다시 검증해 기존 취소·재시작 절차로 복구합니다. 정상적인 대기와 복구 대기를 완료로 처리하지 않습니다.

대화 길이 한도 초과가 확인되면 OpenCode의 대화 정리 기능으로 같은 세션을 정리하고 원래 요청과 최신 플랜으로 이어갑니다. OpenCode가 이미 자동으로 정리·재개 중이면 추가 요청을 보내지 않습니다. 정리 API의 성공 응답만으로 완료를 판단하지 않고, 해당 정리 요청에 연결된 정상 요약과 세션 상태를 확인합니다. 요약 자체를 작업 완료로 처리하지 않으며, 원래 요청 전체와 실행 모델을 유지합니다. 별도로 설정한 대화 정리용 모델이 있으면 그 설정을 따릅니다. 일시적인 정리 실패는 서버의 대기 시각과 1분·3분·최대 10분 간격을 지켜 재시도하고, 결과가 불명확하면 기존 요청의 접수·처리 상태부터 재확인합니다. 화면에는 대화 정리·재시도 대기·원래 작업 재개 상태를 표시하며, 중단·플랜 변경·승인·질문 대기는 복구보다 우선합니다.

대화 정리 도중 앱 소유 OpenCode 프로세스가 종료되면 같은 세션에 다시 연결해 기존 정리 요청의 상태를 확인합니다. 재연결할 때 초기 명령을 다시 전송하지 않습니다. 이전 프로세스의 종료와 남아 있는 정리 기록을 확인한 뒤 필요한 정리·재개를 이어가며, 원래 세션을 확인할 수 없으면 임의의 새 세션으로 바꾸지 않습니다.

승인·질문, 사용자 입력, 중단, 인증·권한 오류와 전송 결과 불명확 상태를 보호합니다. 연결이 끊기면 재조회하며 확인되지 않은 세션에 요청을 중복 전송하지 않습니다. 일반 셸에 자연어 요청을 보내지 않고, OpenCode의 입력 가능한 세션인지 확인합니다. 종료 예약과 해제 뒤에는 새 개선을 시작하지 않습니다. 앱을 다시 열었다는 이유만으로 이전 작업을 재전송하지 않습니다.

Loop 실행 중에는 Windows에 **시스템·디스플레이 사용 중 요청**을 유지해 화면보호기의 자동 실행·화면 꺼짐·자동 절전을 보류합니다. 최소화하거나 트레이로 숨겨도 요청은 유지하며, 중단·완료·Loop 해제·앱 종료 시 해제합니다. 화면보호기 활성값·시간·Windows 전원 계획·시스템 정책·레지스트리는 변경하지 않고 가짜 입력도 보내지 않습니다. 절전에서 복귀하면 전원 요청을 다시 등록합니다.

`PowerSetRequest`의 `DisplayRequired`와 `SystemRequired` 요청을 사용합니다. [Microsoft의 전원 요청 설명](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_power_request_type)에 따른 동작이며, 별도 보안 정책이나 사용자의 잠금·절전 명령을 해제하는 기능은 아닙니다.

## CMD 이어가기와 상태 모니터

태스크 우클릭 또는 터미널 선택 목록의 해당 세션 우클릭에서 **CMD에서 이어가기**를 고르면 확인된 같은 OpenCode 세션을 독립 CMD 창으로 넘깁니다. 플랜 초안을 저장하고 앱 소유 프로세스 종료를 확인한 뒤 이어갑니다. 외부 CMD가 실행 중인 프로젝트의 앱 재실행·아카이브 이동은 차단하며, 앱 종료가 외부 CMD를 종료하지 않습니다. 외부 OpenCode의 로컬 API에서 원래 세션 ID와 프로젝트를 확인하고 해당 세션의 실행 잠금이 유지될 때만 연결 성공으로 표시합니다. 시작 실패 또는 시간 초과 시 이번 시도의 실행 프로세스만 정리하며, 종료한 앱 터미널의 검증된 세션 ID는 보존합니다. 실패 표시 후 같은 CMD 메뉴로 대화를 다시 열 수 있습니다. CMD로 넘긴 대화는 태스크의 ▶, 태스크 우클릭 또는 터미널 탭 우클릭의 **앱 터미널로 가져오기**, 터미널 칸의 **가져오기** 버튼으로 다시 앱 터미널에 넣습니다(앱을 다시 켠 뒤에도 됩니다). 확인 후 앱이 연 CMD 창을 닫고(CMD에서 진행 중인 응답은 중단) 같은 OpenCode 대화를 태스크 터미널에서 이어서 엽니다. 태스크는 중단 상태로 두며 ▶로 플랜을 이어갑니다. 앱이 열지 않은 프로세스가 그 대화를 쓰고 있으면 종료하지 않고 직접 닫도록 안내합니다.

외부 CMD를 닫아 실행 잠금이 해제되면 태스크와 터미널의 시작 버튼으로 기존 세션을 다시 열 수 있습니다. 외부로 넘겼던 이력만으로 재실행을 막지 않으며, 실행 중이거나 종료 확인이 되지 않은 외부 세션은 계속 중복 시작을 차단합니다.

**상태 모니터**는 항상 위의 타일 화면을 열고 기존 터미널을 클릭해 조작합니다. 같은 터미널 화면과 세션, ANSI/TUI·한글·Ctrl+C·터미널 컨텍스트 메뉴를 유지합니다. 녹색은 진행, 주황색은 승인·질문 대기, 회색은 유휴·중단·확인 불가입니다. OpenCode가 실제 진행 중 상태를 보고하면 출력이 잠잠하거나 정체 점검 안내가 있어도 녹색을 유지합니다. 미완료 작업이 남아 있다는 이유만으로 카드를 녹색으로 표시하지 않으며, 종료한 프로세스의 이전 busy 상태도 표시하지 않습니다. 응답 종료와 작업 검증 완료를 구분합니다.

## OpenCode 자동 설치

설치 검사에서는 `.exe`의 Windows 실행 형식을 먼저 확인합니다. npm의 설치 미완료 안내문이 `opencode.exe` 이름으로 남아 있으면 이를 호출하는 CMD/PowerShell 스크립트를 실행하지 않습니다. 이미 설치된 Windows용 본체의 패키지 이름·버전과 `--version` 결과를 확인해 사용하며 사용자 npm 파일은 변경하지 않습니다.

실행 가능한 Windows용 OpenCode가 확인되지 않으면 동의를 받은 뒤 `.env`의 `OPENCODE_INSTALL_COMMAND`(예: `npm install -g opencode-ai`, 여러 명령은 `;`로 연결)에 적은 명령을 Windows PowerShell 창에서 실행합니다. 작업 설정의 **OpenCode 설치** 버튼도 같은 명령을 실행합니다. 이 값은 빌드할 때 앱에 들어가므로 바꾼 뒤 다시 빌드합니다. 별도 설치 스크립트 파일은 쓰지 않습니다.

명시적인 PowerShell 실행 정책을 그대로 따르며, 모든 정책이 미설정인 기본 Windows에서는 그 창에만 RemoteSigned를 적용합니다(npm.ps1 실행용). 명령이 실패하면 창에 오류를 보여 주고 Enter를 누르면 닫히며, 앱도 실패를 알립니다. 값이 없으면 설치하지 않고 `.env`에 명령을 적으라고 안내합니다. 명령도 Windows용 OpenCode를 대상으로 하며 WSL을 호출하지 않아야 합니다.

설치 창이 닫히면 Windows용 OpenCode 설치 상태를 다시 검사하며, 설치 확인에 성공한 경우에만 터미널을 엽니다. 명령의 정상 종료만으로 설치 완료로 간주하지 않습니다. WSL 설치 여부나 배포판은 확인하지 않으며 `wsl.exe`도 실행하지 않습니다.

## 개발·검증·배포

직접 관리하는 실행용 C# 소스는 다음 네 파일에 모았습니다. 테스트와 빌드 중 생성되는 코드는 별도로 유지합니다.

| 파일 | 내용 |
| --- | --- |
| `MainWindow.cs` | 태스크·플랜·아카이브와 메인 창 동작 |
| `TerminalPane.cs` | 터미널 표시·입력·시작 대기·상태 관리 |
| `Services.cs` | OpenCode 통신·작업 흐름·진단·설정 서비스 |
| `Runtime.cs` | 앱 진입점·플랜메이커 등 보조 창·엔진·전송·대체 데스크톱 화면 |

파일 내부의 영역 이름으로 기존 기능을 찾을 수 있습니다. 실행 프로젝트는 빌드 기호로 필요한 영역만 컴파일합니다. 개별 기능 테스트는 선택한 영역을 빌드 중 `obj` 폴더에 추출해 검증하며, 별도로 관리하는 원본 C# 복사본은 두지 않습니다.

Visual Studio에서는 `TerminalNotes.sln`을 엽니다. 솔루션에는 앱과 참조 대상인 `TerminalNotes.TerminalEngine`, 기본 검증 프로젝트가 함께 포함되어 있습니다. 참조 프로젝트를 솔루션에서 제외하거나 언로드하면 NuGet이 프로젝트 정보를 찾지 못할 수 있습니다. .NET 10 개발에는 [Visual Studio 2026 18.0 이상](https://learn.microsoft.com/dotnet/core/install/windows)과 `.NET 데스크톱 개발` 워크로드가 필요합니다. 실행기가 준비하는 앱 실행 환경과 Visual Studio 개발 환경은 별개입니다. `bin`·`obj`를 정리한 후에는 솔루션의 NuGet 패키지 복원으로 중간 파일을 다시 생성합니다.

```powershell
dotnet build .\TerminalNotes.csproj -c Release
dotnet run --project .\tests\Documents\TerminalNotes.DocumentTests.csproj -c Release
dotnet run --project .\tests\TabDocuments\TerminalNotes.TabDocumentTests.csproj -c Release
dotnet run --project .\tests\SleepPrevention\TerminalNotes.SleepPreventionTests.csproj -c Release
dotnet run --project .\tests\StartupDispatch\TerminalNotes.StartupDispatchTests.csproj -c Release
dotnet run --project .\tests\UI\TerminalNotes.UiTests.csproj -c Release
dotnet publish .\TerminalNotes.csproj -c Release -r win-x64 --self-contained false -o .\dist\win-x64
```

세 실행기(`Start-TerminalNotes.cmd`, `Start-TerminalNotes-Updated.cmd`, `Start-TerminalNotes.ps1`)와 `launcher.app.json`은 모두 `dist\win-x64`의 실행 파일을 사용합니다. 세 실행기의 공통 처리는 `Invoke-TerminalNotes.ps1`에 있으며, CMD 진입점인 `Ensure-TerminalNotes.cmd`도 같은 처리를 호출합니다. .NET 준비 → 배포 파일 확인 → 누락 시 위 `dotnet publish` → 정리 → 앱 실행 순서입니다. 프로젝트를 복사할 때 이 실행 도우미들과 `Clean-BuildArtifacts.ps1`도 함께 옮깁니다. 자동 설치는 이 세 실행기를 통해 시작할 때 적용됩니다. 게시할 때는 이 폴더만 갱신하며, 수정할 때마다 별도의 날짜별 배포 폴더를 만들 필요가 없습니다. i런처에 이미 설치한 버전이 있으면 설치된 실행 파일이 우선하므로 i런처의 설치·업데이트 경로로 새 버전을 적용해야 합니다. `bin\Release`의 빌드나 원본 `dist`의 갱신만으로는 기존 설치가 갱신되지 않습니다.

프로젝트를 반복 전송할 때 소스, `Assets`, `docs`, 테스트 코드와 현재 실행용 `dist\win-x64`는 유지합니다. 각 프로젝트의 `bin`·`obj`는 다시 빌드할 수 있는 중간 결과물입니다. `artifacts`에는 별도 터미널 실행용 `artifacts\terminal-desktop-win-x64`만 남기며, 과거 배포본·검증 결과는 두지 않습니다(테스트가 필요할 때 다시 만듭니다). 작업 기록·플랜·설정은 보존합니다.

게시와 검증을 마친 뒤 프로젝트 루트에서 다음 정리 명령을 실행합니다. `Clean-BuildArtifacts.ps1`은 정해진 소스 프로젝트의 `bin`·`obj`를 검사해 삭제하고, 삭제 용량과 배포 파일 보존 여부를 확인합니다. `-Apply`를 생략하면 삭제 없이 미리보기만 표시합니다. 게시나 검증에 실패한 경우에는 정리하지 않습니다.

```powershell
powershell -NoProfile -File .\Clean-BuildArtifacts.ps1 -Apply
```

.NET 준비와 실행기 변경은 `powershell -NoProfile -File .\tests\LauncherBootstrap\Test-Launchers.ps1`로 검증합니다. 격리된 모의 호스트·설치 응답을 사용해 설치 상태 판별, 실패 시 실행 차단, 게시·정리·실행 순서와 경로 전달을 확인하며 실제 SDK 설치나 사용자 앱 실행은 하지 않습니다.

UI 테스트는 실제 사용자 폴더/세션 대신 임시 프로젝트와 설정을 사용합니다. `$env:TERMINALNOTES_UI_INDEPENDENT_ONLY='1'`은 실제 네이티브 OpenCode에서 플랜 없는 시작·자동 요청 없음·기존 태스크 보존·중단/시작 및 세션 복원·아카이브/CMD 분리를 검사합니다. 모델 요청은 보내지 않습니다. `$env:TERMINALNOTES_UI_NATIVE_ADD_ONLY='1'`은 기본 네이티브 화면에서 터미널 추가·선택·닫기 후 기존 화면과 실행 상태·출력이 보존되는지 검사합니다. `$env:TERMINALNOTES_UI_COMPOSER_ONLY='1'`을 설정하면 모델을 호출하지 않고 임시 창에서 플랜 입력창·초안·고정 슬롯의 배정/교환/보존을 검증합니다. 포커스를 검사하므로 다른 WPF UI 테스트와 동시에 실행하지 않습니다. 이 UI 테스트 실행기는 마우스·키보드를 검사하며, 테스트 환경의 WPF 종료 시 펜 장치 조회 대기를 피하도록 stylus/touch 지원을 끕니다. 펜·터치 입력은 검증 범위에 포함되지 않습니다. `InputJournal`은 질문 비저장·전역 지침 병합과 저장 충돌을, `AutoResumeController`/`OpenCodeRecovery`/`PlanDispatch`/`StartupDispatch`는 로컬 테스트 서버와 이벤트로 자동 진행·시작 재시도·중복 전송 방지를 검증합니다. `SleepPrevention`은 모의 전원 요청의 수명주기와 실제 Windows 요청의 등록·해제 전후 화면보호기 활성값·대기 시간 보존을 검증합니다. 실제 화면보호기 실행을 기다리는 테스트는 아닙니다. 모의 테스트 통과를 실제 모델이나 보안 정책의 실제 동작 검증으로 간주하지 않습니다.

실제 터미널을 시작하지 않고 화면 배치·초안·슬롯·상태 표시만 검증하려면 `TERMINALNOTES_UI_COMPOSER_ONLY=1`과 `TERMINALNOTES_UI_COMPOSER_NO_TERMINAL=1`을 함께 설정합니다. 생존 상태를 흉내 내는 임시 PowerShell 대기 프로세스는 사용하지만 실제 터미널 시작·중단·CMD 연결 검사는 실행하지 않으며 결과에도 이 검증 범위를 표시합니다.

터미널 분리 검사는 `TERMINALNOTES_UI_INPUT_ONLY=1`로 실행합니다. 임시 PowerShell 터미널 두 개에서 한쪽 크기 변경을 의도적으로 지연시킨 동안 다른 쪽 명령 실행과 원래 프로세스 종료를 확인합니다. `TERMINALNOTES_UI_EXIT_ONLY=1`은 15초 종료 준비 시간 초과 뒤 입력·작업 기록이 유지되는지 검사합니다. `tests/Terminal`은 네이티브 작업 분리와 종료를, `tests/UiResponsiveness`는 UI가 막힌 동안의 로그와 복구·오류 기록을 검증합니다. UI 모드 환경 변수는 하나만 설정하고 순서대로 실행합니다.

화면 미리보기는 위 `COMPOSER_ONLY` 모드에 `TERMINALNOTES_UI_DESIGN_PREVIEW`를 절대 PNG 경로로 지정합니다. 임시 프로젝트와 정적인 터미널 예시로 화면만 캡처하며 모델을 실행하거나 일반 smoke 검사를 대신하지 않습니다. `TERMINALNOTES_UI_DESIGN_WIDTH`(기본 1480, 최소 820), `TERMINALNOTES_UI_DESIGN_LAYOUT`(1~6, 기본 2)로 좁은 창과 분할 화면을 확인할 수 있습니다. 일반 검사를 실행할 때는 미리보기 환경 변수를 해제합니다.

과거 `Automation*`의 3역할 실행 테스트는 이전 구현의 자료입니다. 현재 앱의 사용자 경로에서는 역할 자동화가 비활성화되어 있습니다. 실제 모델을 호출하는 테스트는 별도 명시적 요청이 있을 때만 실행합니다.
## 작업 알림

검증된 작업 완료, 명확한 실행 오류, 지속적으로 확인된 장시간 정체에 Windows 알림을 표시합니다. 단순한 터미널 무출력이나 잠깐의 대기, 승인·질문·입력 대기는 알리지 않습니다. 같은 실행의 같은 상태는 한 번만 알리고, 알림을 표시하기 직전에도 해당 작업 상태를 다시 확인합니다.

창의 메뉴 또는 트레이 아이콘 우클릭 메뉴에서 **작업 알림**을 선택하면 알림 사용·영구 끄기와 **5·10·30·60분**, **사용자 지정 시간(분)** 동안 알림 중지를 설정할 수 있습니다. 중지 시간이 끝나면 자동으로 다시 켜지고, 설정은 재시작 후에도 유지됩니다. 중지 중 끝난 작업의 완료 알림을 나중에 몰아서 표시하지 않습니다.


## 자동 업데이트 (GitHub Actions)

`main`에 푸시하면 self-hosted Windows 러너가 `.github/workflows/release.yml`로 다음 버전(csproj 버전 이상, 직전 릴리스 +1)을 정해 게시하고 `TerminalNotes-win-x64.zip`을 GitHub Release로 올립니다. 앱은 실행할 때 최신 릴리스를 확인해 새 버전이 있으면 업데이트할지 묻고, 내려받은 뒤 앱을 닫으면 파일을 교체하고 다시 시작합니다. 작업 폴더·플랜·설정·`공지.md`는 유지되며, 실행 중인 터미널이 있으면 업데이트하지 않고 알림만 표시합니다.

설치는 릴리스의 `TerminalNotes-Setup.exe`로 합니다. 실행하면 묻지 않고 바로 설치한 뒤 앱을 시작합니다. .NET이 없는 PC에서도 실행되며, .NET 10이 없으면 함께 들어 있는 실행 환경을 앱 폴더(`dotnet\`)에 설치합니다(관리자 권한·인터넷 불필요). 처음 실행하면 작업 폴더만 고르고(기본 `C:\opencode`) 일반 모드·Auto Mode로 바로 시작합니다. 관리자 권한 없이 `%LOCALAPPDATA%\Programs\TerminalNotes`(이미 설치돼 있으면 그 위치)에 설치하고 시작 메뉴·바탕 화면 바로 가기와 Windows "앱" 목록(제거)을 만듭니다. 사용자 폴더라서 이후에는 앱이 GitHub 릴리스의 zip으로 스스로 업데이트합니다. 다시 실행하면 같은 위치를 새 버전으로 바꾸며 설정·작업·`공지.md`는 유지합니다. 배포 스크립트용 옵션: `/S`(조용히), `/dir=경로`, `/nodesktop`, `/nolaunch`; 제거는 설치 폴더의 `uninstall.exe /uninstall [/S]`. 조용한 실행 결과는 `%TEMP%\TerminalNotes-Setup.log`에 남습니다.

빌드는 `build\Publish-Release.ps1` 하나로 끝납니다(`out\TerminalNotes-Setup.exe` 약 79MB·.NET 10 실행 환경 포함, `out\TerminalNotes-win-x64.zip` 약 6MB, `out\win-x64`). 러너에는 **.NET 10 SDK만** 있으면 되고, 외부 라이브러리는 `lib\`에 들어 있어 NuGet 다운로드 없이(인터넷 없이) 빌드됩니다. 직접 실행: `powershell -NoProfile -ExecutionPolicy Bypass -File build\Publish-Release.ps1 [-Version 1.0.130]`. 사용자 PC에는 WebView2 Runtime(Windows 11 기본 포함)이 필요합니다.

설정: `.env`에 `UPDATE_GITHUB_API`(GitHub Enterprise는 `https://<호스트>/api/v3`, github.com은 `https://api.github.com`, 비우면 러너에서 빌드할 때 그 러너의 GitHub 주소), `UPDATE_REPOSITORY`(소유자/이름), 비공개 저장소면 읽기 전용 `UPDATE_TOKEN`, `UPDATE_ASSET`을 채우면 빌드 때 `update.json`으로 앱 옆에 들어갑니다(`.env.sample` 참고). 러너에는 저장소 시크릿 `TERMINALNOTES_ENV`(.env 전체 내용) 또는 러너 PC의 `.env` 경로를 가리키는 환경 변수 `TERMINALNOTES_ENV_PATH`를 둡니다. 러너에서 빌드할 때 `UPDATE_REPOSITORY`가 비어 있으면 그 러너의 저장소와 API 주소를 자동으로 씁니다(토큰은 `.env`의 `UPDATE_TOKEN`). 업데이트 확인 결과(꺼짐·최신·새 버전·실패 이유)는 상단 버전 표시에 마우스를 올리면 보입니다. 저장소를 읽을 수 없으면(토큰 없음·권한 없음) "릴리스 없음"으로 넘기지 않고 상태 줄에 알립니다. 업데이트 기록은 `%LOCALAPPDATA%\TerminalNotes\updates\update.log`에 남습니다.
